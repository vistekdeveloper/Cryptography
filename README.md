
## What this project does

The system sends menu information from the server to the client and also sends end-of-day sales data back to the server.

Because this data is sent over a network, there is a risk that someone could could read or change the data.

To reduce these security issues, we added extra some patches.

## What we added

### 1. HMAC for menu integrity

HMAC is generated by using the pre-shared key (the server and client knows the key) and the data.
The server will generate the HMAC and send it with the data to the client.
The client will use the pre-shared key to verify the menu by comparing the HMAC it generated with the HMAC the server sent.

If the HMAC matches that means the file passes integrity check, if it fails means the file has been tampered.

### 2. TLS for the communication channel

Raw TCP connection is not encrypted, this means anyone one the network regardless if its public wifi, can read the content sent over the traffic. Therefore we use TLS to encrypt the connection between the server and the client. 

Since the cert is self generated, we use "context.verify_mode = ssl.CERT_NONE" since no actual CA signed it. The client will request the server.crt and then the server will prove that its the legit server by solving a challenge using it server.key (private key).Instead of sending a symmetric key over the network, both the client and server independently compute the same symmetric session key using a key exchange algorithm (ECDHE) and use it to encrypt all subsequent communication.


## Simple summary

We added:
- HMAC to protect the menu data from modification
- TLS to encrypt the network traffic between the server and client

This makes the system much safer for use over public Wi-Fi.
